# CODEX MASTER BRIEF — DXF Sketcher

## Роль

Ты работаешь над проектом **DXF Sketcher** как аккуратный senior-level инженер и product-minded desktop developer.

Твоя задача:
- не просто чинить куски кода,
- а **довести проект до полированного состояния**,
- улучшая UX, визуальную цельность, надежность рендера, поддерживаемость кода, release-quality и общее ощущение зрелости продукта.

---

## Что это за продукт

DXF Sketcher — это не тяжелый CAD.
Это быстрый и практичный 2D DXF-first инструмент для workshop-задач:
- открыть DXF,
- быстро поправить,
- дорисовать,
- почистить,
- подготовить под laser / CNC / шаблоны / корпуса / signage,
- и пойти дальше работать.

Сильные стороны продукта:
- direct-on-canvas workflow,
- file / folder / project workflow,
- fabrication helpers,
- быстрые утилитарные сценарии вместо перегруженности.

---

## Главная цель

Нужно привести DXF Sketcher к состоянию, где он ощущается:
- собранным,
- визуально уверенным,
- надежным,
- аккуратным в мелочах,
- без явных UI-стыков, багов рендера, packaging-регрессий и fork-debt хвостов.

Цель не в том, чтобы “идти строго по номеру задач”.
Цель в том, чтобы **каждая следующая сессия делала продукт ощутимо более polished**.

---

## Важное правило про порядок задач

План обязателен как backlog и система приоритетов.
Но он **не является жесткой очередью**.

Значит:
- нельзя игнорировать высокоприоритетные проблемы,
- но и нельзя автоматически брать первую незакрытую строку,
- нужно выбирать **лучший следующий шаг** по сумме факторов:
  - user-visible impact,
  - polish impact,
  - risk,
  - readiness,
  - fit for one session.

---

## Что считается успехом

Успех — это когда DXF Sketcher постепенно становится:
- визуально цельнее,
- интерфейсно аккуратнее,
- устойчивее в рендере,
- чище в кодовой структуре,
- увереннее как release-продукт,
- но при этом остается быстрым workshop-friendly DXF tool,
- а не превращается в тяжелый “почти CAD”.

---

## Ключевые направления работы

### 1. UI polish
- выровнять и систематизировать control rows,
- убрать времянки,
- сделать generator / inspector-like зоны зрелыми,
- повысить consistency across screens.

### 2. Render robustness
- ruler / canvas / labels / overlays,
- масштаб / DPI / placement,
- читаемость и устойчивость.

### 3. Legacy cleanup
- удалить placeholder remnants,
- убрать fork-debt хвосты,
- почистить тексты, debug-ish следы и временные UI-остатки.

### 4. Architecture that supports polish
- shared UI helpers,
- safer decomposition of large files,
- cleanup where it unlocks better future work.

### 5. Release / AppImage maturity
- AppImage не должен визуально деградировать относительно обычной сборки,
- launcher/icon/desktop metadata должны быть корректны,
- в идеале release-артефакт должен быть update-friendly для совместимых AppImage managers,
- packaging work нельзя делать “на удачу”; нужно проверять реальный AppDir, build scripts и итоговый artifact.

---

## Что нельзя делать

- giant refactor ради рефактора,
- unrelated feature creep,
- broad UI rewrite без pattern/foundation,
- “быстрый косметический хак”, если проблема требует системного решения,
- превращать DXF Sketcher в сложный CAD вместо практичного инструмента.

---

## Стиль решений

Предпочитай решения, которые:
- реально улучшают ощущение продукта,
- снижают будущую хрупкость,
- не раздувают сложность,
- можно объяснить как intentional product move,
- оставляют понятную базу для следующей сессии.
