# DXF Sketcher — Polish Standard

Этот файл описывает, как выглядит **полированное состояние** проекта.

Не спрашивай только “работает ли”.
Спрашивай:
- выглядит ли зрелым,
- ощущается ли цельным,
- надежно ли ведет себя,
- не оставляет ли ощущения сырости,
- не разваливается ли как release artifact.

---

## 1. Visual consistency

Хорошо, когда:
- spacing ритмичный,
- control rows собраны по одной логике,
- units визуально встроены в систему,
- primary actions читаются сразу,
- разные панели будто части одного продукта.

Плохо, когда:
- каждая строка параметров выглядит как отдельная самоделка,
- отступы, ширины и alignment случайны,
- разные панели будто из разных версий приложения,
- части UI ощущаются времянкой.

---

## 2. Interaction consistency

Хорошо, когда:
- одинаковые задачи решаются одинаковыми паттернами,
- toggles/selectors/buttons ведут себя предсказуемо,
- control rows легко сканировать взглядом,
- пользователь быстро понимает, где value, где unit, где mode, где main action.

---

## 3. Rendering robustness

Хорошо, когда:
- ruler labels читаемы,
- подписи и деления не разваливаются от zoom,
- canvas overlays ведут себя устойчиво,
- DPI / scale factor не ломают визуальную логику.

Плохо, когда:
- текст читается как каша,
- геометрия элементов смещается,
- поведение “случайно нормальное” только в одном масштабе.

---

## 4. Product maturity feel

Хорошо, когда:
- нет мусорных или placeholder текстов,
- диалоги и поповеры ощущаются законченными,
- нет явных fork-debt следов,
- стартовый экран, панели, генераторы и toolbar воспринимаются как единый продукт.

Плохо, когда:
- видны “временные” строки,
- меню или подписи выглядят недоделанными,
- отдельные зоны сильно отстают по качеству.

---

## 5. Release / packaging maturity

Хорошо, когда:
- AppImage не визуально хуже обычной сборки,
- launcher icon, desktop entry и metadata согласованы,
- иконки внутри самого приложения не исчезают и не заменяются заглушками,
- package-specific path не ломает базовое впечатление от продукта,
- release artifact ощущается как first-class build, а не как “ну хоть запускается”.

Плохо, когда:
- часть иконок исчезает только в AppImage,
- сборочный fallback silently ухудшает итоговый artifact,
- release metadata неполная,
- update story на Linux выглядит недоделанной, хотя технически могла бы быть лучше.

---

## 6. Code health that supports polish

Хорошо, когда:
- повторяющиеся UI-паттерны вынесены,
- большие файлы постепенно разгружаются по ответственности,
- правки не требуют лезть в монолит без нужды,
- код проще читать и безопаснее менять.

Плохо, когда:
- каждая новая UI-правка собирается с нуля,
- одна зона слишком многое знает обо всем,
- для простого polish-шага приходится открывать полпроекта.

---

## 7. Workshop-first identity

DXF Sketcher должен оставаться:
- быстрым,
- утилитарным,
- точным,
- practical-first,
- не перегруженным CAD-сложностью.

Любой polish должен усиливать именно это.

---

## 8. Definition of a good session

Хорошая сессия:
- улучшила видимую часть продукта или сняла очевидную шероховатость,
- не перегрузила проект лишним масштабом изменений,
- оставила понятную основу для следующего шага,
- зафиксирована в worklog.

---

## 9. Quick evaluation checklist

Перед тем как считать шаг удачным, спроси:
- Стало ли заметно аккуратнее или надежнее?
- Стало ли меньше ощущение сырости?
- Улучшилась ли цельность интерфейса?
- Упростился ли следующий логичный шаг?
- Не утащил ли этот шаг продукт в heavy-CAD сторону?
- Не ухудшился ли AppImage / release artifact?
- Обновлен ли worklog?
